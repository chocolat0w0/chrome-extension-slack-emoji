# Slack絵文字作成Chrome拡張：設計と段階別検証

作成日: 2026-10-31
状態: 個人利用向けの実装・実機正常系検証を実施済み。未検証環境は検証記録に記載。Step 6の配布・導入手順整備も完了。新規プロファイル検証はユーザー指定で省略した。

## 0.3.0の変更

ユーザー指定によりGoogle Fontsを利用時取得する。ゴシック・太いゴシックはNoto Sans JP、明朝はNoto Serif JP、丸文字はZen Maru Gothic。Google Fontsの2ドメインに限定したhost_permissionsと取得用Service Workerを追加。初期版の外部通信なし・ローカルフォントのみという制約を変更する。入力本文・名前・画像はGoogleに送らず、書体・Unicode範囲のリクエストを送る。詳細は `../../validation/web-fonts.md`。以下の初期設計と異なる部分は本変更を優先する。

## 目的と決定事項

Slackのカスタム絵文字登録ページで、文字絵文字の作成から登録までを完結させる。画像のダウンロード、ファイル探し、リネーム、別サイトとの往復をなくす。

ユーザーが選択した方針はChrome拡張。以下の初期仕様・技術選定・段階分けは実装に向けた提案であり、ユーザーが個別に指定したものではない。

- 初期対象はChromeのPC版と、ユーザーが現在使うカスタム絵文字登録ページ。
- 現在のワークスペースにログイン済みで、本人に絵文字追加権限があることを前提とする。
- 登録ページに作成欄を追加し、画像と名前を既存フォームへ渡す。
- 初期版の最終保存はユーザーがSlackの保存ボタンを押す。
- 画像はブラウザ内で生成し、通常の操作ではダウンロードしない。ブラウザ内部のキャッシュ等によるディスク利用まで禁止する意味ではない。
- バックエンド、Slack OAuth、非公開APIの直接呼び出し、Cookie・セッショントークンの取得は初期構成に含めない。

## 検討した方式

| 方式 | 利点 | 制約・採用判断 |
| --- | --- | --- |
| 登録ページへのUI追加 | 作成と登録が一つの画面でつながる | SlackのDOM変更への対応が必要。初期案として採用 |
| Chromeサイドパネル | エディターの表示をSlackのレイアウトから独立させやすい | フォーム連携は同様に必要。埋め込みUIが不安定な場合の代替 |
| Slackアプリ | Slackの標準UIから利用できる | 公式追加APIはEnterprise向け。今回の対象外 |

既存の作成サイトの埋め込みは採用せず、必要な文字描画機能を拡張内に実装する。既存サイト固有のフォントや表現の再現は別途検討する。

## 初期版の体験と機能

1. 対応するSlack登録ページを開くと、既存UIを隠さずに作成欄が表示される。
2. 文字、改行、文字色、背景色または透過、Slack登録名を入力する。
3. 拡大プレビューと、リアクションに近い小さなサイズのプレビューを確認する。
4. 「Slackの登録欄に反映」を押すとPNGと登録名が既存フォームへ渡る。
5. Slack側のプレビューと登録名を確認して保存する。
6. 連続作成する場合は作成欄に戻る。Slack側の完了を確認できない限り、拡張は「登録完了」と表示しない。

初期仕様の提案:

- 128×128pxの静止PNG。これは本拡張の出力仕様であり、Slackの必須寸法という意味ではない。
- テキストは1〜4行、各行最大12書記素を目安とした入力上限。上限超過を黙って切り捨てない。
- 太字のシステムフォントを使用し、全行に共通の文字サイズを描画領域に合わせて調整する。可読性はユーザーがプレビューを目視して判断する。システムでは可読性の保証、文字の小ささを理由とする警告・短縮案内・登録制限を行わない（ユーザー指定）。
- 結合文字を途中で分割しない。日本語、英数字、記号で検証する。カラー絵文字や機種間のフォント一致は保証範囲外。
- 初期背景は透過。文字色・背景色はプリセットと色指定を用意する。
- 登録名は文字画像の内容とは独立した入力欄。初期版では自動翻訳・ローマ字変換をしない。
- 登録名は空欄を禁止する。使用可能文字・長さは実機調査で確認してから制約を決め、重複や最終的な可否はSlackの判定を表示する。
- 出力は128,000バイト未満をアプリ側の保守的な上限とする。超過時は反映を止める。
- 「登録欄への反映」と「登録完了」を明確に区別する。
- テンプレート保存、履歴、GIF、画像取り込み、一括登録、ブラウザをまたぐ同期は後続候補。

## 構成

Manifest V3、JavaScript ES Modules、素のDOM、Canvas 2Dを採用する。外部依存パッケージは使用しない。順序固定の限定ビルド、Node標準テスト、Chrome上の実Canvas・模擬フォーム検証を使用する。

データの流れ:

`入力 → 描画モデル → Canvas → PNG Blob → File → Slackのファイル入力・名前入力 → ユーザーの保存操作`

| 部品・予定ファイル | 責務 |
| --- | --- |
| `manifest.json` | 実機で確認したURLに限定してコンテンツスクリプトを読み込む |
| `src/content.js` | 対象画面の判別、UIの取り付け・取り外し、再表示への追従 |
| `src/editor/view.js` | 入力フォーム、プレビュー、反映ボタン、エラーの表示 |
| `src/editor/model.js` | 入力値の型、初期値、入力検証 |
| `src/emoji/render.js` | フォント準備、文字サイズ計算、Canvas描画、PNG生成 |
| `src/slack/adapter.js` | Slackフォームの発見、画像と名前の設定、受理状態の観測 |
| `src/editor/styles.css` | Shadow DOM内の表示、フォーカス、明暗背景への対応 |
| `tests/` | 描画・入力検証と、模擬Slackフォームに対するブラウザ検証 |

Slack固有のDOM知識はadapterに集約する。Step 1で確認した専用data-qa属性を中心に、入力型・所属フォーム・ダイアログの位置関係を組み合わせる。対象が一意に決まらない場合は操作しない。aria-modalがfalseのダイアログも検出し、保存ボタンの無効状態はdisabledとaria-disabledの両方で判断する。開閉でダイアログidが変わるため毎回要素を再取得する。

コンテンツスクリプトはISOLATED worldで動作させ、共有DOMを介して連携する。ページ内部のReact状態や非公開関数への依存を避ける。UIはShadow DOMでスタイルを分離するが、Shadow DOMをセキュリティ境界として扱わない。

初期案ではService Workerも永続ストレージも不要。manifestのURL範囲はStep 1で確定する。登録ページが別URLへリダイレクトされる場合も調査し、Slack全体へのアクセスを初めから要求しない。外部フォントや外部スクリプトを読み込まず、入力内容を外部に送信しない。

## Step 1：実際の登録画面を調査する

**目的:** どのURL・DOM・画面遷移を支援するかを固定する。

- 対象ページのURL、リダイレクト、画像追加ダイアログ、ファイル入力、名前入力、保存結果の表示場所を確認する。
- UIの言語とChromeのバージョンを記録する。
- 名前の制約、重複エラー、ダイアログを閉じて再度開いた場合のDOMを調べる。
- 登録権限がない画面やログイン画面で、拡張を出さない判定を決める。
- 取得した記録にCookie、トークン、個人情報を含めない。

**成果物:** `docs/validation/slack-form-observation.md`。URLパターン、要素の検出方針、未確認事項を記録。

**完了条件:** 対象フォームを一意に特定でき、manifestの対応範囲を決められる。

## Step 2：ダウンロード不要の受け渡しを検証する

**目的:** エディター実装前に、最大の不確実性を解消する。

- 検証専用の最小拡張を用意する。
- 固定のテスト文字からPNGを生成し、BlobからFileを作る。
- DataTransferでFileListを構成して対象inputに設定し、必要なinput/changeイベントを発火する方式を試す。
- 登録名を設定し、Slackが画像と名前を受け取ってプレビューすることを確認する。
- 一意のテスト名で1件保存し、絵文字一覧に現れることを確認する。検証用ワークスペースを優先し、会社のワークスペースを使う場合はテスト登録対象を事前に明確にする。
- 再表示後にも繰り返し受け渡しができること、ダウンロード操作が発生しないことを確認する。

**成果物:** `docs/validation/slack-upload-spike.md`。試した方式、実際の結果、対応Chrome・画面、残る制約を記録する。検証コードは製品コードと区別する。

**完了条件:** 実際のSlackで、ファイル保存を挟まず画像・名前を渡し、ユーザーの保存操作で1件登録できる。

**成立しない場合:** dropイベント方式を追加調査する。両方式とも受理されなければ、ダウンロード不要要件は未達と記録して設計を見直す。サイドパネルへの変更だけでは受け渡し問題は解決しない。非公開APIへの依存へ黙って切り替えない。明示的なPNGダウンロードは縮小案として提示できるが、当初の完了条件とはしない。

## Step 3：文字絵文字エディターを作成・検証する

実施状況: 単独画面で実装済み。依存なしのJavaScriptモジュールとNode標準テストを採用する構成へ変更。Chromeの実Canvasで8ケースの寸法・容量・端の透過画素を確認。詳細は `../../validation/emoji-editor.md`。Slackへの組み込みはStep 4で行う。

**依存:** Step 2が成立していること。

- 入力モデル、Canvas描画、PNG生成、作成UIを実装する。
- フォントの準備完了後に描画する。古い非同期描画結果で新しいプレビューを上書きしない。
- 空文字、日本語1〜4行、長い英数字、結合文字、透過背景、濃色背景を検証する。
- PNGの寸法と容量、実際の画素、文字の欠けをブラウザで確認する。Canvasのモックだけで描画品質の合格判定をしない。
- 小さなサイズのプレビューが生成画像を正しく表示すること、キーボードで入力・色選択・反映操作ができることを確認する。文字が読めるかどうかは合格条件に含めない。

**完了条件:** 指定した内容を、欠けのない128×128px PNGとして出力できる。

## Step 4：Slack画面に統合する

実施状況: 実装・ビルド・Chromeの模擬フォーム10項目が完了。新しいdist拡張の実Slackで表示・反映・再反映・下書き保持を確認済み。ユーザーによる最終保存後、登録一覧と再読み込み後の保持も確認済み。Step 4完了。詳細は `../../validation/slack-editor-integration.md`。

- 作成UIを登録画面に取り付け、Step 2で成立した方式をadapterとして実装する。
- DOM再生成に追従し、UIの二重追加やイベントの多重登録を防ぐ。監視は対象範囲に限定し、離脱時に解除する。
- 反映中は二重操作を止める。反映済みの画像を編集した場合は再反映が必要と表示する。
- ダイアログが閉じた場合や対象が変わった場合は古い要素へ書き込まない。
- 画像だけ反映され名前の設定が失敗した場合など、部分的な反映を成功扱いしない。
- Slackのプレビューを確認できなければ、ファイル入力の設定だけで「反映済み」と断定しない。
- エラー時は編集内容を保持する。認証切れ・権限不足・重複名のエラーはSlack側の案内と矛盾しない表示にする。

**完了条件:** 一つのページで作成・反映・手動保存ができ、フォーム消失や再表示から復帰できる。

## Step 5：回帰テストと実利用確認

実施状況: Chromeで模擬フォームの追加9項目・既存10項目を確認。名前のaria-invalidを反映済み判定へ追加修正。実Slackの異常系・英語UI・別環境は未検証。詳細は `../../validation/regression.md`。

| 検証層 | 確認すること |
| --- | --- |
| ロジックテスト | 入力境界、行数、書記素、容量判定、描画サイズ計算 |
| ブラウザテスト | 実CanvasのPNG生成、FileList受け渡し、フォーム再生成、連打、対象が複数ある場合の停止 |
| 実Slackでの手動テスト | 正常登録、重複名、閉じて再表示、2件連続登録、ページ再読込、既存の手動アップロードが機能すること |
| 表示確認 | 日本語・英語の対象UI、ライト・ダーク表示、狭いウィンドウ、キーボード操作、小さなサイズのプレビューが生成画像を正しく表示すること |

模擬フォームでの合格はSlackとの互換性を保証しない。実機で確認できなかった言語・環境・権限条件は未検証として残す。実Slackへの自動反復登録はテストに組み込まない。

**完了条件:** Step 2の登録経路が製品版でも成立し、テスト結果と対応環境が記録されている。

## 最初の判断ポイントと後続候補

最初に実施するのはStep 1〜2。ここで成立性を判断し、失敗した場合はエディターの作り込みに進まない。Step 3以降は検証結果で設計を更新したうえで進める。

後続候補は、配色テンプレート、フォント追加、登録名候補、履歴、複数サイズの比較、一括生成。ワンクリック登録は、保存成功・失敗・重複・再送の判定が安定してから検討する。

## 根拠と未検証の境界

- ChromeコンテンツスクリプトはDOMを操作できる。ISOLATED worldとページはDOMを共有する: https://developer.chrome.com/docs/extensions/develop/concepts/content-scripts
- CanvasからBlobを生成できる: https://developer.mozilla.org/en-US/docs/Web/API/HTMLCanvasElement/toBlob
- FileをDataTransferに追加できる: https://developer.mozilla.org/en-US/docs/Web/API/DataTransferItemList/add
- file inputにFileListを設定できる: https://html.spec.whatwg.org/multipage/input.html
- Slackは正方形・128KB未満・透過背景を推奨し、画像と名前を指定して保存する登録手順を案内している: https://slack.com/help/articles/206870177-Add-custom-emoji-and-aliases-to-your-workspace

上記はブラウザ機能とSlackの通常手順の根拠であり、生成したFileを現在のSlack画面が受理することを保証する資料ではない。その成立性はStep 2で確認する。
